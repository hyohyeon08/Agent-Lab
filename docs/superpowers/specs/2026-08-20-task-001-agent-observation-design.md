# Task 001 에이전트 관찰 설계

- 날짜: 2026-08-20
- 상태: 사용자 승인 완료
- 범위: `STUDY-0001`의 첫 번째 실행인 `RUN-0001`

## 1. 개요

Agent Lab의 첫 번째 연구 도구로 작은 TypeScript 예약 시스템 픽스처를 만든다.
하나의 고정된 Codex 에이전트에게 사용자 버그 제보만 전달하고, 에이전트가
문제를 탐색하고 재현 테스트를 작성하고 수정하고 검증하고 완료를 판단하는
과정을 관찰한다.

이번 단계의 목적은 에이전트 성능을 비교하는 것이 아니다. 한 에이전트의
관찰 가능한 행동을 읽고 기록하는 방법을 만들고, 이후 연구를 이끌 질문을
발견하는 것이 목적이다.

## 2. 연구 질문

첫 번째 탐색 질문은 다음과 같다.

> 하나의 고정된 Codex 에이전트는 작은 TypeScript 버그를 어떻게 조사하고
> 수정하며, 그 과정에서 어떤 관찰 가능한 행동을 기록할 가치가 있는가?

이 질문은 탐색적이다. `RUN-0001` 하나만으로 에이전트의 일반적인 특성이나
다른 모델·하네스와의 우열을 결론 내리지 않는다.

## 3. 목표

- 실제 코드처럼 보이지만 사람이 전체 구조를 이해할 수 있는 작은 픽스처를
  만든다.
- 시작 시 공개 테스트와 타입 검사는 통과하지만 사용자에게 드러나는 버그가
  있는 상태를 만든다.
- 에이전트가 버그 제보를 바탕으로 직접 재현 테스트를 작성할 수 있게 한다.
- 관찰 대상 Agent와 연구 준비·평가 Agent를 분리한다.
- 정답과 외부 평가를 관찰 대상 Agent의 실행 공간에서 제외한다.
- 실행 메타데이터, 프롬프트, diff, 평가, 관찰과 해석을 재현 가능한 형태로
  보존한다.
- 첫 실행에서 발견한 불편을 바탕으로 다음 자동화 여부를 판단한다.

## 4. 비목표

- 여러 Agent, Model 또는 Harness 비교
- 통계적 성능 주장
- 자동 Trace 수집 플랫폼
- 데이터베이스, 대시보드 또는 범용 Runner
- 실제 시간대, 날짜, 반복 일정까지 다루는 완전한 예약 제품
- 관찰 대상 Agent로부터 정보를 적대적으로 숨기는 보안 경계 구축

외부 평가를 실행 공간에서 분리하는 목적은 실험 오염을 줄이는 것이다. 강한
보안 격리를 제공하려는 것이 아니다.

## 5. 연구 단위와 식별자

- Study: `STUDY-0001`
- Condition: `codex-current-config-v0`
- Task: `TASK-001`
- Run: `RUN-0001`

`codex-current-config-v0`은 실행 시점에 사용자가 선택한 Codex 설정 전체를

## 6. 역할 분리

### 6.1 연구 준비 Agent

현재 Agent Lab 작업이 이 역할을 맡는다.

- 픽스처와 의도적인 결함 작성
- 외부 평가 작성 및 사전 검증
- 실행용 작업 공간 준비
- 연구 메타데이터와 관찰 양식 준비

### 6.2 관찰 대상 Agent

이전 설계 맥락이 없는 새로운 Codex 작업이 이 역할을 맡는다.

- 실행용 `booking-scheduler` 폴더만 프로젝트로 사용
- 사용자 버그 제보만 전달받음
- 일반적인 Codex 작업 방식으로 조사, 수정, 테스트 및 완료 판단
- 실행 중 Model, reasoning effort, plugin 및 skill 설정을 변경하지 않음

### 6.3 평가 및 분석 Agent

관찰 대상 Agent가 완료를 선언한 뒤 현재 Agent Lab 작업이 다시 이 역할을
맡는다.

- 결과 상태와 최종 diff 고정
- 공개 테스트, 타입 검사, 외부 평가 실행
- 수동 diff 및 회귀 테스트 검토
- 관찰 기록과 저널 작성 지원

관찰 대상 Agent가 자신의 결과를 외부 평가하고 다시 수정하게 하지 않는다.
외부 평가 이후의 수정은 별도 Run으로 취급한다.

## 7. 예약 도메인 규칙

### 7.1 시간 표현

예약 시간은 같은 날의 분 단위 정수로 표현한다. 예를 들어 09:00은 `540`,
10:00은 `600`이다. 날짜와 시간대 처리는 이번 픽스처 범위에서 제외한다.

### 7.2 시간 구간

예약은 시작 시각을 포함하고 종료 시각을 포함하지 않는 반개구간으로 본다.

```text
[startMinute, endMinute)
```

따라서 `[540, 600)`과 `[600, 660)`은 겹치지 않는다.

두 시간 구간 `a`, `b`의 올바른 겹침 규칙은 다음과 같다.

```text
a.startMinute < b.endMinute && b.startMinute < a.endMinute
```

### 7.3 유효성

- `startMinute < endMinute`여야 한다.
- 시작과 종료가 같으면 잘못된 입력이다.
- 종료가 시작보다 빠르면 잘못된 입력이다.
- 같은 회의실의 시간이 실제로 겹칠 때만 충돌로 판단한다.
- 다른 회의실은 같은 시간에도 예약할 수 있다.

## 8. 의도적인 결함

고장 난 초기 상태는 경계가 닿는 경우까지 겹친다고 판단한다.

```text
a.startMinute <= b.endMinute && b.startMinute <= a.endMinute
```

이 결함 때문에 기존 예약이 10:00에 끝나고 새 예약이 10:00에 시작하는 경우,
실제로는 겹치지 않지만 충돌 오류가 발생한다.

공개 테스트에는 인접 예약 사례를 포함하지 않는다. 따라서 고장 난 초기
상태에서도 공개 테스트와 타입 검사는 통과한다.

## 9. 관찰 대상 Agent에게 전달할 프롬프트

다음 문장을 변경하지 않고 `prompt.md`에 저장한 뒤 새 Codex 작업에 전달한다.

```text
예약 생성 기능에 버그가 있습니다.

기존 예약이 10:00에 끝나고 새로운 예약이 10:00에 시작하면
두 예약의 시간이 실제로 겹치지 않는데도 중복 예약 오류가 발생합니다.

원인을 조사하고 문제를 수정해 주세요.
재발을 방지할 수 있는 테스트도 추가해 주세요.
기존의 실제 중복 예약 방지 동작은 유지되어야 합니다.
```

파일명, 결함 위치, 비교 연산자, 테스트 위치, 작업 순서는 추가로 알려주지
않는다. 특히 "테스트부터 작성하라"는 지시를 넣지 않는다.

## 10. 픽스처 구조

```text
benchmarks/fixtures/booking-scheduler/
├── package.json
├── package-lock.json
├── tsconfig.json
├── README.md
├── src/
│   ├── booking.ts
│   ├── time-range.ts
│   ├── booking-repository.ts
│   └── booking-service.ts
└── test/
    └── booking-service.test.ts
```

### 10.1 파일 책임

- `booking.ts`: 예약 입력과 저장 데이터 타입만 정의한다.
- `time-range.ts`: 시간 구간 유효성 검사와 겹침 판단만 담당한다.
- `booking-repository.ts`: 회의실별 예약 조회와 메모리 저장을 담당한다.
- `booking-service.ts`: 입력 검증, 기존 예약 조회, 충돌 검사, 예약 생성을
  조합한다.
- `booking-service.test.ts`: 관찰 대상 Agent에게 공개되는 기존 동작을
  검증한다.

픽스처는 TypeScript, Node 내장 테스트 실행기, `tsx`만 사용한다. 네트워크,
데이터베이스, 웹 프레임워크, 날짜 라이브러리는 사용하지 않는다.

### 10.2 공개 테스트

고장 난 초기 상태의 공개 테스트는 다음을 검증한다.

- 첫 예약 생성 성공
- 같은 회의실에서 일부 시간이 겹치는 예약 거부
- 기존 예약과 충분한 간격이 있는 예약 허용
- 다른 회의실에서 같은 시간의 예약 허용
- 시작과 종료가 같을 때 입력 오류
- 종료가 시작보다 빠를 때 입력 오류

인접한 예약을 허용하는 테스트는 넣지 않는다.

### 10.3 픽스처 README

픽스처 README에는 설치, 공개 테스트, 타입 검사 명령과 일반적인 API 사용법만
설명한다. 반개구간 규칙, 의도적인 결함, 외부 평가 사례, 정답 구현은 설명하지
않는다.

## 11. 외부 평가기

```text
benchmarks/evaluators/booking-scheduler/TASK-001/
├── evaluator.test.ts
├── oracle.patch
└── README.md
```

외부 평가기는 후보 코드를 수정하지 않고 실행 결과만 반환한다. 실행용 작업
공간에는 복사하지 않는다. `oracle.patch`는 의도적인 결함만 바로잡는 최소
정답 패치이며 평가기 사전 검증에만 사용한다.

Agent Lab 루트에서 다음 형태의 명령으로 후보 작업 공간을 평가한다.

```text
npm run evaluate:task-001 -- --candidate <후보 booking-scheduler 절대 경로>
```

평가기 명령은 후보 경로를 명시적으로 받아 공개된 모듈 API를 호출한다. 후보
파일을 복사, 수정 또는 포맷하지 않으며, 모든 외부 사례가 통과할 때만 종료
코드 `0`을 반환한다.

### 11.1 자동 평가 사례

- 기존 예약 종료와 새 예약 시작이 같은 경우 허용
- 새 예약 종료와 기존 예약 시작이 같은 경우 허용
- 일부 시간이 겹치는 경우 거부
- 새 예약이 기존 예약을 완전히 포함하는 경우 거부
- 기존 예약이 새 예약을 완전히 포함하는 경우 거부
- 시작과 종료가 완전히 같은 예약 거부
- 다른 회의실의 같은 시간 예약 허용
- 시작과 종료가 같은 잘못된 시간 구간 거부
- 종료가 시작보다 빠른 잘못된 시간 구간 거부

### 11.2 평가기 사전 검증

관찰 대상 Agent를 실행하기 전에 다음 상태를 증명한다.

1. 정상 정답 구현에서 공개 테스트, 타입 검사, 외부 평가가 모두 통과한다.
2. 고장 난 초기 상태에서 공개 테스트와 타입 검사는 통과한다.
3. 고장 난 초기 상태에서 외부 평가의 인접 예약 사례는 실패한다.
4. 고장 난 초기 상태에서도 실제 중복, 다른 회의실, 잘못된 시간 구간 사례는
   예상한 결과를 낸다.

정상 정답 구현 검증은 고장 난 픽스처의 임시 복사본에 `oracle.patch`를
적용하여 수행한다. 추적되는 고장 난 원본 픽스처는 변경하지 않는다.

### 11.3 수동 평가

평가 및 분석 Agent가 다음을 검토한다.

- Agent가 회귀 테스트를 추가했는가?
- 테스트가 실제 사용자 제보를 재현하는가?
- 특정 시각 `10:00`에만 맞춘 구현이나 테스트가 아닌가?
- 기존 중복 방지 규칙을 우회하지 않았는가?
- 관련 없는 파일이나 지나치게 많은 코드를 수정하지 않았는가?

## 12. 실행용 작업 공간

```text
runs/workspaces/STUDY-0001/RUN-0001/
└── booking-scheduler/
```

`runs/workspaces/`는 Agent Lab Git에서 제외한다. 실행 전 고장 난 픽스처만
복사하고 해당 `booking-scheduler` 폴더를 독립된 Git 저장소로 초기화한다.
첫 커밋은 Agent가 작업하기 전의 정확한 시작 상태를 나타낸다.

새 Codex 작업은 이 폴더만 로컬 프로젝트로 사용한다. 다음 항목은 실행용
작업 공간에 포함하지 않는다.

- 외부 평가기
- 정답 구현
- Agent Lab 연구 및 설계 문서
- 현재 설계 대화
- 예상되는 행동이나 평가 사례

관찰 대상 Agent가 지정된 작업 공간 밖의 Agent Lab 파일을 읽었다는 증거가
있다면 해당 실행은 `contaminated`로 기록하고 분석 대상에서 제외한다.

## 13. 실행 절차

### 13.1 실행 전

1. 정답 구현으로 평가기 전체 통과를 확인한다.
2. 고장 난 초기 상태로 돌아가 공개 테스트와 타입 검사 통과, 외부 평가 실패를
   확인한다.
3. 실행용 작업 공간을 만들고 독립 Git 저장소의 시작 커밋을 생성한다.
4. `STUDY-0001`과 `RUN-0001` 메타데이터를 작성한다.
5. 화면에 표시되는 Agent 설정과 정확한 프롬프트를 기록한다.

환경 준비가 실패하면 Agent 실행을 시작하지 않는다. 준비 오류를 수정한 뒤
같은 `RUN-0001`을 시작할 수 있다.

### 13.2 실행 중

- 새 Codex 작업에 확정된 프롬프트만 전달한다.
- 힌트, 작업 순서, 파일 위치를 추가로 알려주지 않는다.
- 잘못된 방향을 바로잡거나 테스트 실행을 재촉하지 않는다.
- 권한이나 도구 문제로 진행이 불가능한 경우에만 최소한으로 개입한다.
- 모든 사람 개입은 시점, 이유, 전달 내용을 기록한다.

도메인 또는 구현 힌트를 제공했다면 해당 실행은 `contaminated`로 기록한다.
중립적인 권한 승인이나 환경 복구는 개입으로 기록하되 자동으로 오염으로
판단하지 않는다.

### 13.3 실행 완료 후

1. Agent가 완료를 선언한 즉시 결과 상태를 고정한다.
2. 최종 응답을 `final-response.md`에 저장한다.
3. 시작 커밋을 기준으로 `diff.patch`를 생성한다.
4. Agent가 실행했다고 주장한 검증과 실제 출력 근거를 구분해 기록한다.
5. 공개 테스트와 타입 검사를 새로 실행한다.
6. 외부 평가를 실행한다.
7. 회귀 테스트와 최종 diff를 수동 검토한다.
8. 사실 기반 행동 기록과 별도의 해석을 작성한다.

외부 평가가 실패해도 같은 Agent 작업을 다시 열어 수정시키지 않는다. 최초
상태를 `RUN-0001`로 보존하고, 후속 시도는 새 Run ID를 사용한다.

## 14. 연구 기록 구조

```text
experiments/STUDY-0001/
├── study.yaml
└── runs/
    └── RUN-0001/
        ├── run.md
        ├── prompt.md
        ├── final-response.md
        ├── evaluation.yaml
        └── diff.patch
```

### 14.1 `study.yaml`

연구 질문, Study ID, Task ID, Condition, 고정 Agent 설정, 픽스처 시작 버전을
기록한다.

### 14.2 `run.md` 메타데이터

```yaml
study_id: STUDY-0001
run_id: RUN-0001
date: 2026-08-20

agent:
  label: codex-current-config-v0
  model: unknown
  reasoning_effort: unknown
  harness: Codex desktop
  plugins: unknown

fixture:
  name: booking-scheduler
  start_commit: required-before-run

task:
  id: TASK-001

source_task:
  id: required-after-task-creation
  url: required-after-task-creation

human_interventions: 0
contaminated: false
```

### 14.3 실행 전 기록

Agent 실행 전에 다음을 작성한다.

- 연구 질문
- 예상하는 행동 순서
- 특히 관찰하고 싶은 행동
- 한 번의 실행으로 결론 내릴 수 없는 내용

### 14.4 사실 기반 행동 기록

```markdown
| 순서 | 행동 유형 | 대상 | 관찰된 결과 |
|---:|---|---|---|
| 1 | inspect | package.json | 테스트 명령 확인 |
| 2 | test | 전체 테스트 | 기존 테스트 통과 |
```

행동 유형은 다음 다섯 개로 시작한다.

- `inspect`: 파일과 저장소 탐색
- `test`: 테스트와 평가 실행
- `edit`: 코드 또는 테스트 수정
- `command`: 설치, Git 및 기타 명령
- `communicate`: Agent가 밖으로 표현한 계획, 가설, 완료 판단

정확한 시간이 제공되지 않으면 시간을 추측하지 않고 행동 순서만 기록한다.
숨겨진 사고 과정은 기록하지 않는다.

### 14.5 해석

사실 기반 행동 기록과 분리하여 다음을 작성한다.

- 유용해 보였던 행동
- 불필요하거나 위험해 보였던 행동
- 실패 후 복구 방식
- 실행 전 예상과 달랐던 점
- 이 실행의 한계
- 다음에 검증할 질문

### 14.6 `evaluation.yaml`

```yaml
public_tests: pass
typecheck: pass
external_evaluation: pass

regression_test:
  added: true
  quality: acceptable

diff:
  files_changed: 2
  lines_added: 12
  lines_deleted: 1
  review: acceptable

human_intervention:
  count: 0
  details: []

contaminated: false
final_result: pass
```

`quality`와 `review`는 수동 판단임을 결과 해석에서 명시한다. 예시의 숫자는
목표값이 아니며 실제 결과로 교체한다.

## 15. 데이터 흐름

```text
정상 구현으로 평가기 검증
        ↓
고장 난 픽스처 상태 검증
        ↓
실행용 독립 저장소 생성
        ↓
새 Codex 작업에 사용자 제보 전달
        ↓
Agent의 자율적인 조사·수정·검증
        ↓
완료 선언 시 결과와 diff 고정
        ↓
공개 테스트 + 타입 검사 + 외부 평가
        ↓
수동 diff·회귀 테스트 검토
        ↓
사실 기반 행동 기록
        ↓
해석·한계·다음 질문 기록
```

## 16. 오류 및 예외 처리

### 16.1 준비 오류

의존성 설치, 시작 상태 생성, 평가기 사전 검증이 실패하면 Run을 시작하지
않는다. 준비 오류는 연구 결과로 세지 않는다.

### 16.2 실행 환경 오류

권한 승인이나 도구 장애 해결처럼 도메인 지식을 제공하지 않는 개입은 세부
내용을 기록한다. 결과 해석에서 사람 개입이 있었음을 명시한다.

### 16.3 실험 오염

다음 중 하나가 발생하면 `contaminated: true`로 기록한다.

- Agent가 외부 평가, 정답 구현 또는 설계 문서를 읽음
- 사람이 결함 위치나 수정 방법에 관한 힌트를 제공함
- 실행 중 Agent 설정을 변경함
- 시작 상태가 사전 검증한 상태와 다름

오염된 실행의 Trace는 학습 자료로 볼 수 있지만 Agent 성능 또는 정식 Study
결과에는 포함하지 않는다.

### 16.4 외부 평가 실패

실패 결과를 그대로 보존한다. 동일 작업을 이어서 수정하지 않고, 필요하다면
실패 원인을 질문으로 삼아 별도 Run을 설계한다.

### 16.5 메타데이터 부재

Model 이름, reasoning effort, 시간, token 정보를 확인할 수 없으면 `unknown`으로
기록한다. 값을 추정하거나 다른 지표로 대체하지 않는다.

## 17. 구현 완료 기준

다음 항목이 모두 충족되어야 Task 001 연구 도구 구현이 완료된다.

- 픽스처가 문서화된 명령으로 설치됨
- 고장 난 초기 상태에서 공개 테스트와 타입 검사가 통과함
- 고장 난 초기 상태에서 외부 평가의 인접 예약 사례가 실패함
- 정상 정답 구현에서 공개 테스트, 타입 검사, 외부 평가가 모두 통과함
- 실행용 작업 공간에 정답과 외부 평가 파일이 없음
- 실행용 작업 공간이 독립 Git 저장소이며 시작 상태를 커밋으로 식별할 수 있음
- 확정된 사용자 프롬프트가 별도 파일에 보존됨
- Study 및 Run 기록 템플릿이 준비됨
- 외부 평가가 후보 코드를 변경하지 않음
- 동일한 깨진 시작 상태를 다시 생성할 수 있음
- 실험 오염과 사람 개입을 기록할 수 있음

## 18. 설계상 선택하지 않은 대안

### 공개 실패 테스트 제공

구현은 단순하지만 Agent가 사용자 제보를 재현하고 회귀 테스트를 설계하는
행동을 관찰할 수 없어서 선택하지 않았다.

### 현재 설계 대화의 Agent를 관찰 대상으로 사용

결함 위치와 정답 기준을 이미 알고 있어 관찰이 오염되므로 선택하지 않았다.

### Agent Lab 저장소 전체를 관찰 대상에게 제공

외부 평가와 설계 문서를 발견할 수 있어 별도 실행용 저장소를 사용한다.

### 첫 단계부터 여러 Agent 비교

관찰 언어와 평가 방법이 검증되지 않은 상태에서 비교하면 숫자는 만들 수 있어도
행동 차이를 해석하기 어려워 선택하지 않았다.

## 19. RUN-0001 이후 결정

`RUN-0001`을 완료한 뒤 근거를 바탕으로 다음 중 하나만 선택한다.

- 같은 Task를 같은 Agent로 반복하여 실행 간 변동 관찰
- 다른 작은 버그인 Task 002 작성
- 누락된 행동을 반영해 관찰 기록 양식 수정
- 모호했던 완료 판단을 줄이도록 평가 절차 개선

첫 실행 전에 이 후속 작업을 미리 구현하지 않는다.
