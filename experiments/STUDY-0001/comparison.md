# STUDY-0001 5회 반복 비교 보고서

## 연구 질문

동일한 `gpt-5.6-luna`/`high`/플러그인 비활성 조건의 Codex 에이전트가 같은 작은 예약 경계 버그를 다섯 번 해결할 때, 결과와 관찰 가능한 작업 과정은 얼마나 일관되는가?

## 비교 조건

- 고정 프롬프트: 다섯 실행의 `prompt.md`가 바이트 단위로 동일하다.
- 고정 fixture: `booking-scheduler`, 시작 커밋 `bd932cab3f9a5fae3d5836b4173888bcb46aade3`, 시작 tree `febe76de742d3435b1af566121ed8ea430f76a8e`.
- 고정 Agent 조건: `gpt-5.6-luna`, reasoning effort `high`.
- 플러그인 조건: 사용자 설정을 무시하고 plugins와 recommended plugins를 비활성화했다. RUN-0002~0005의 세션 `world_state`에서 `plugins_instructions: false`를 확인했고 Superpowers 지시나 호출은 없었다. RUN-0001도 같은 조건으로 별도 확인돼 있다.
- 사람 개입: 모든 실행 0회.
- 독립성: 각 실행은 별도 Git 저장소와 별도 Codex 작업을 사용했다. 관찰 대상에는 초기 프롬프트 이후 메시지를 보내지 않았다.
- 평가: 공개 테스트, 타입 검사, 외부 9개 사례, 회귀 테스트 결함 탐지 확인, 수동 diff 검토를 관찰 대상 종료 후 별도로 수행했다. 결함 탐지 확인은 추가된 테스트가 기존 결함을 실제로 드러내는지 검증한다.

## 관찰 가능한 과정 비교

### 공통 패턴

다섯 실행은 모두 파일과 관련 구현·테스트를 먼저 읽고 `TimeRange.overlaps`의 닫힌 구간 비교를 원인으로 선택했다. 그다음 구현과 회귀 테스트를 하나의 편집 동작에서 함께 바꾸고, 수정 후 공개 테스트와 타입 검사를 실행했다. 마지막에는 diff 또는 Git 상태를 확인하고 완료를 선언했다.

따라서 다음 항목은 5/5로 일치했다.

- 시간 구간 값 객체를 수정 지점으로 선택
- 반개구간 `[시작, 종료)` 규칙 적용
- 실제 부분 중복 차단 유지
- 구현 파일과 서비스 수준 테스트 파일만 변경
- 구현과 회귀 테스트를 같은 편집 동작에서 변경한 뒤 검증 명령 실행
- 관찰 대상 실행 중 실패한 명령 없음

### 달라진 부분

- RUN-0001~0003은 파일 열거 뒤 관련 파일을 넓게 읽었고, RUN-0004~0005는 먼저 키워드 검색으로 위치를 좁혔다.
- RUN-0002와 RUN-0004는 테스트·타입 검사를 한 연결 명령으로 실행했다. RUN-0003과 RUN-0005는 별도 명령으로 실행했다. 결과에는 차이가 없었다.
- RUN-0005만 인접 예약의 양방향을 공개 테스트로 고정했다. 나머지 네 실행은 사용자 제보 방향 한 개만 추가했지만, 구현은 외부 평가의 반대 방향도 통과했다.
- RUN-0004는 편집 전에 Git 상태와 빈 diff를 한 번 더 확인했다.

## 독립 평가와 복구

각 실행의 추가 회귀 테스트만 고장 난 baseline에 적용하면 RUN-0001~0004는 해당 경계 테스트 1개, RUN-0005는 양방향 테스트 2개가 실패했다. 즉 모든 공개 회귀 테스트는 결함을 실제로 재현한다. 수정 결과는 모든 외부 평가 사례를 통과했다.

관찰 대상 Agent 자체에는 실패 후 복구 사례가 없었다. 평가 인프라에서는 RUN-0001 외부 평가기의 샌드박스 IPC 오류와 RUN-0002~0005 결함 탐지 확인 자동화 명령 오류가 있었지만, 모두 후보 코드를 바꾸지 않고 평가 명령만 수정해 복구했다. 이는 Agent 행동 비교 항목으로 계산하지 않았다.

## 해석

이번 다섯 실행에서 결과의 일관성은 높았다. 성공률은 5/5이고 구현 선택도 5/5로 같았다. 작은 경계 조건 버그에 대해 Luna-high 조건은 사용자 제보를 일반적인 시간 구간 규칙으로 확장해 해결했다.

작업 과정도 일관됐다. 5/5 모두 관련 파일을 조사하고 구현과 회귀 테스트를 함께 편집한 뒤 테스트·타입 검사·diff 확인으로 결과를 검증했다. 실행 간 의미 있는 차이는 공개 테스트 범위였다. 4/5는 제보 방향 하나를, 1/5는 대칭 경계까지 명시했다.

이 결과는 “이 조건이 항상 성공한다”는 통계적 결론이 아니라, 첫 fixture에서 관찰된 안정적인 결과 패턴과 반복되는 절차 패턴이다. 다음 단계에서는 모델을 바꾸기보다 다른 작은 버그 유형의 fixture를 추가해, 구현 난이도와 조사 경로가 달라져도 같은 패턴이 유지되는지 확인하는 편이 유용하다.

## 한계

- 하나의 작은 TypeScript fixture와 하나의 프롬프트만 사용했다.
- 다섯 실행은 통계적 대표성을 제공하지 않는다.
- 표시된 메시지·명령·파일 변경만 비교했고 숨겨진 추론은 평가하지 않았다.
- RUN-0002~0005의 동시 실행은 벽시계 시간과 인프라 자원 사용에 영향을 줄 수 있다.
- host skill 목록은 표시됐지만 skill 호출은 없었으며, 플러그인 지시는 비활성화됐다.

## 다음 연구

두 번째 fixture는 같은 Luna-high/플러그인 비활성 조건을 유지하되, 단순 비교 연산자 변경이 아닌 작은 상태 전이 또는 데이터 변환 버그로 만든다. 같은 사용자 제보 전용 프롬프트를 사용하고 다음 질문을 관찰한다.

1. 같은 Agent 조건에서 다른 유형의 작은 버그를 해결할 때도 결과의 일관성과 과정의 변동이 함께 나타나는가?
2. 여러 실행과 fixture에서 Model 요청 프록시 및 상위 Tool Call 봉투 수가 증가할수록 토큰 사용량도 반복해서 증가하는가?

두 번째 질문은 RUN-0002와 RUN-0004에서 논리 Tool Call 수는 같지만 Model–Tool 왕복 구조와 토큰 수가 달랐다는 관찰에서 나온 탐색 가설이다. Tool 내용과 반환량, 실행 인프라의 영향이 있으므로 후속 자료에서도 같은 관계가 반복되는지 확인한다.
