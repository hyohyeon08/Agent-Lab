# STUDY-0002 5회 반복 비교 보고서

## 연구 질문

동일한 `gpt-5.6-luna`/`high`/플러그인 비활성 조건의 Codex Agent가 작은 재고
상태 전이 버그를 다섯 번 해결할 때, 결과의 일관성과 관찰 가능한 과정의 변동은
어떻게 나타나는가?

탐색 질문은 Model 요청과 Tool 왕복 수가 늘 때 total input도 함께 증가하는지,
그리고 cache를 분리한 새 Context 처리량과 비용도 같은 방향으로 움직이는지다.

## 비교 조건

- 다섯 `prompt.md`는 같은 사용자 버그 제보다.
- fixture source commit은
  `db148723b9899c89b29634786a827a127c2df340`으로 고정했다.
- 모델은 `gpt-5.6-luna`, reasoning effort는 `high`로 고정했다.
- plugins와 recommended plugins를 비활성화했고 Superpowers 지시·호출은 없었다.
- 각 실행은 별도 Git 저장소와 새 Codex 작업을 사용했고 사람 개입은 0회였다.
- 벽시계 간섭을 줄이기 위해 RUN-0002~RUN-0005도 병렬이 아니라 순차 실행했다.
- 종료 뒤 공개 테스트·타입 검사·외부 9개 사례·회귀 테스트의 baseline 결함
  탐지·수동 diff 검토를 독립적으로 수행했다.

## 과정의 공통점과 차이

5/5 실행에서 다음 패턴이 반복됐다.

- 파일 목록을 확인한 뒤 서비스·재고·저장소·공개 테스트를 읽었다.
- 읽기 뒤 재취소가 `release`에 도달하는 것을 원인으로 설명했다.
- 구현과 회귀 테스트를 하나의 편집 Tool에서 함께 변경했다.
- 편집 뒤 첫 공개 테스트와 타입 검사가 통과했다.
- 관련된 구현 파일과 테스트 파일 외에는 변경하지 않았다.
- Tool 실패, 테스트 실패, 재시도와 Skill 호출이 없었다.

달라진 부분은 주로 종료 전 확인 방식이었다.

- RUN-0001~0002는 검증 뒤 diff를 별도 shell 호출로 확인했다.
- RUN-0003은 별도 diff 확인 뒤 최종 줄 번호를 한 번 더 읽었다.
- RUN-0004는 테스트·타입 검사·diff 검사를 하나의 Tool 호출로 묶었다.
- RUN-0005는 편집 전에 `tsconfig`와 Git log를 추가로 읽고, 검증 명령은
  RUN-0004처럼 묶었다.

평균 input/request는 15,564~16,280, peak context는 17,536~18,718로 비교적 좁은
범위였다. 이 조건에서는 요청 수가 5→6→7회로 늘 때 total input도 대체로

그러나 새 Context 처리량과 비용은 같은 순서가 아니었다. 요청이 가장 많은
RUN-0003은 cache 비율이 가장 높아 uncached input이 가장 적었다. 반대로
RUN-0002는 요청 수가 평균과 같지만 마지막 응답 프록시가 cache miss로 기록돼
uncached input과 추정 비용이 가장 컸다. 따라서 비용을 설명하려면 왕복 수뿐
아니라 cache hit 패턴과 output을 함께 봐야 한다.

5회 total input은 475,855, uncached input은 106,959, total tokens는 483,822다.
API 정가 추정 합계는 $0.03833012다. 이는 2026-08-24의 Luna 텍스트 토큰 정가를
사용한 비교용 추정치이며 실제 Codex 청구액은 아니다.

## 연구 질문에 대한 현재 답

첫 번째 질문에는 “이번 작은 상태 전이 버그에서도 결과는 매우 일관됐고 과정은
작게 변동했다”고 답할 수 있다. 성공, 구현 지점, 핵심 회귀 테스트와 첫 시도
성공은 5/5로 같았다. 추가 read, 검사 순서, Tool 명령 묶음과 cache 패턴은
실행마다 달랐다.

탐색 질문에는 두 층의 답이 필요하다.

1. 요청 수와 total input: 호출당 Context 크기가 비슷해 함께 증가하는 패턴이
   반복됐다.
2. 요청 수와 uncached input·비용·시간: cache와 각 응답 단계 지연 때문에
   단순한 증가 관계가 관찰되지 않았다.

이는 인과 결론이 아니라 두 fixture에서 얻은 후속 가설이다. 더 복잡한 fixture,
긴 Tool 출력 또는 실패·복구가 있는 과제에서도 같은 구조가 유지되는지 확인해야
한다.

## 한계

- 작은 TypeScript fixture 하나를 5회 실행한 자료다.
- 같은 모델·하네스 조건만 다뤘으므로 모델 또는 하네스 간 우열을 말할 수 없다.
- 표시된 메시지·명령·파일 변경만 관찰했고 숨겨진 추론은 평가하지 않았다.
- 모델 요청과 응답 단계 시간은 Trace 프록시이며 제공자 내부 telemetry가 아니다.
- cache hit 여부는 Agent 행동 외의 서버·세션 처리에도 영향을 받을 수 있다.
- 테스트 명령을 묶은 실행은 주된 목적 하나로 Tool을 분류하므로 명령 내부
  세부 작업 수와 논리 Tool 호출 수가 같지 않다.
