## 관찰

### 결과는 매우 일관적이었다

다섯 실행 모두 `ReservationService.cancel()`에서 현재 예약이 이미
`cancelled`인지 검사하고, `Inventory.release()` 전에 예약 복사본을 반환하는
해법을 선택했다. 재고 수량에 상한을 적용하거나 특정 입력만 예외 처리하는
우회 수정은 없었다.

회귀 테스트도 모두 같은 예약을 두 번 취소한 뒤 반환값과 최종 재고를 확인했다.
RUN-0001·0003~0005는 `cancelled` 상태를 별도로 assertion했고, RUN-0002는
첫 번째와 두 번째 반환값의 동등성으로 상태를 간접 확인했다. 외부 평가에서는
모든 구현이 완료 예약 취소 방지, 다른 예약과의 격리와 기존 생성 동작까지
통과했다.

### 큰 작업 경로도 반복됐다

모든 실행은 대체로 다음 순서를 따랐다.

    파일 목록 확인
    → 서비스·재고·저장소·기존 테스트 읽기
    → 중복 release를 원인으로 설명
    → 구현과 회귀 테스트를 한 번에 편집
    → 테스트와 타입 검사
    → diff 확인 및 완료

세부 과정에는 차이가 있었다. RUN-0003은 최종 줄 번호를 다시 읽었고,
RUN-0005는 편집 전에 `tsconfig.json`과 Git log를 추가로 확인했다.
RUN-0004와 RUN-0005는 테스트·타입 검사·diff 검사를 한 Tool 호출에 묶었다.

## 오늘 배운 점

1. 다른 유형의 작은 버그에서도 결과 일관성과 과정 변동이 함께 나타났다.
   STUDY-0001은 시간 경계 버그, STUDY-0002는 상태 전이 버그였지만 두 연구 모두
   5/5 성공했고 핵심 구현 선택도 각 연구 안에서 일관됐다.

2. total tokens만 보면 Agent가 실제로 새로 처리한 Context 비용을 알 수 없다.
   cached input과 uncached input을 분리해야 실행 간 비용 차이를 더 잘 설명할 수
   있다.

3. Model↔Tool 왕복이 늘면 호출당 Context가 비슷한 조건에서 total input은
   증가할 수 있다. 하지만 cache hit가 높으면 uncached input과 비용은 같은
   방향으로 증가하지 않을 수 있다.

4. Tool 호출 수만으로 속도를 판단할 수 없다. 각 모델 응답의 지연, Tool 호출에
   포함된 작업과 cache 상태를 함께 봐야 한다.

5. 최종 성공 여부만으로는 첫 수정의 정확성을 구분할 수 없다. 이번에는
   `first_pass_success`가 5/5였기 때문에 시행착오나 실패 복구 행동을 관찰하지
   못했다.

## 현재 가설

1. 관련 조회와 검증을 적절히 묶어 불필요한 Model Request를 줄이면 total input을
   줄일 수 있다.
2. 비용은 total input보다 uncached input, cache hit와 output token 조합으로
   설명하는 편이 더 정확하다.
3. 작은 버그에서는 같은 Agent 조건이 안정적인 결과를 내지만, 이 결과가 더
   복잡한 과제까지 유지되는지는 아직 알 수 없다.
4. 실패·복구가 필요한 과제에서는 첫 시도 성공 과제보다 왕복 수와 uncached
   input의 변동이 더 크게 나타날 가능성이 있다.

현재 자료는 이 가설들의 출발점이며 인과관계를 증명하지 않는다.
